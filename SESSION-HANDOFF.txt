1. WHAT PROJECT NOVA IS
-------------------------------------------------------------------------------

A private-server ecosystem for Fortnite 7.40 (Chapter 1 Season 7,
UE 4.22, CL-5046157). Players run a launcher; matches are peer-to-peer —
the gameserver runs on a player's own PC, elected by a coordinator.

Five components:

  Main backend/       Fastify + TypeScript. Full EOS translation layer, XMPP,
                      MCP profiles, matchmaking, diagnostics. Port 3551 (game)
                      / 3552 (host agent).
  Launcher/           Tauri app (Rust + React/TS). Launches the game, runs the
                      local backend + proxy, hosts matches, auto-updates.
  Launcher/cobalt/    Cobalt — C++ DLL loaded INTO the Fortnite client.
                      Redirects Epic hosts to 127.0.0.1:3551. Also carries the
                      UE4 reflection layer and the intro bumper.
  Project-Reboot-DLL/ Project Reboot — C++ DLL injected into a client to turn
                      it into the gameserver.
  coordinator/        Linux box that holds demand and runs host election.
  nova-proxy/         Small Node proxy on 3551 -> coordinator / local agent.

4. HOW TO BUILD AND RELEASE (exact, in order)
-------------------------------------------------------------------------------

Full detail is in RELEASING.md. The short version that actually works:

  # 1. Build the native DLLs if you changed them
  pwsh "Launcher\cobalt\build.ps1"            -> Launcher/cobalt/x64/Release/Cobalt.dll
  MSBuild "Project-Reboot-DLL\Project Reboot.sln" /p:Configuration=Release /p:Platform=x64
                                              -> Project-Reboot-DLL/x64/Release/Project Reboot.dll

  # 2. Stage EVERYTHING into the launcher payload (this is the classic trap)
  node tools/stage-backend.mjs            # compiles Main backend -> dist
  node tools/stage-cobalt.mjs             # Cobalt.dll -> 4 consumed copies
  node tools/stage-cobalt.mjs reboot      # Project Reboot.dll -> 4 copies

  # 3. VERIFY the staging (run all three; they are the only thing between
  #    "fixed in source" and "fixed on a player's machine")
  node tools/stage-backend.mjs --check
  node tools/stage-cobalt.mjs --check
  node tools/stage-cobalt.mjs reboot --check

  # 4. Bump the version in THREE files (they must match)
  Launcher/src-tauri/tauri.conf.json   package.version
  Launcher/package.json                version
  Launcher/src-tauri/Cargo.toml        version   (line 3, NOT line 55)

  # 5. Build the installer
  cd Launcher && npx tauri build --features custom-protocol

  # 6. Sign EXPLICITLY. The build prints an error about TAURI_PRIVATE_KEY and
  #    produces NO .sig — that is expected, you sign manually:
  npx tauri signer sign -f "C:/Users/Admin/.nova-updater/nova-updater.key" -p "" \
    "src-tauri/target/release/bundle/nsis/Project Launcher_<ver>_x64-setup.nsis.zip"
  #    Windows cannot hold an empty env var, which is why -p "" is used.
  #    ALWAYS confirm the .sig exists and md5 the zip AFTER signing.

  # 7. latest.json + GitHub release (must be marked --latest)
  gh release create v<ver> --repo JustAdev742/Project-Jovian --latest \
     --title "..." --notes-file <notes> \
     "<...setup.exe>" "<...setup.nsis.zip>" latest.json

  # 8. VERIFY THE SERVED ARTEFACTS (always do this):
  #    - curl releases/latest/download/latest.json -> version matches
  #    - its signature == the local .sig file contents
  #    - md5 of the served zip == md5 of the signed zip
  #    - gh api .../releases/latest -> tag_name is the new one

  # 9. Copy latest.json to the repo root and commit it.

VERSIONING RULE LEARNED THE HARD WAY: never go backwards. The updater only
moves forward, so a player on a withdrawn version would be stranded forever.
(1.8.7/1.8.8 were deleted from GitHub; we released 1.8.9 rather than reusing
1.8.6 for exactly this reason.)

5. RECENT WORK — WHAT WAS DONE AND WHY (most recent first)
-------------------------------------------------------------------------------

1.9.2  QUICKBARS LOOKUP USED THE WRONG NAME.  *** UNVERIFIED — TEST THIS ***
       Symptom: client reached the match (Join succeeded / EnterAircraft /
       ExitAircraft all present in FortniteGame.log) but NEVER left the
       loading screen.
       Cause: Inventory::GetQuickBars asked the controller for a property
       named "QuickBars". 7.40 has no such property -> returned null ->
       ServerAddItemInternal was never called for any item -> no item GUID was
       ever mapped to a quickbar slot. The client logged, once per item:
           AFortQuickBars::AddItemInternal could not find Item with GUID ...
           World Inventory received        <- the inventory itself arrived fine
       and then waited forever for an inventory that could not be built.
       Server-side this appeared only as "Failed to find property 'QuickBars'",
       twice, which reads like a harmless probe.
       The answer was in the same file: Inventory::Update calls
       FortPlayerController.OnRep_QuickBar — SINGULAR. A UE4 rep notify is
       named after its property.
       Fix (inventory.cpp): three routes — "QuickBars", then "QuickBar", then
       find the AFortQuickBars actor by its Owner (cannot be misspelled). The
       property result is checked with IsA(FortQuickBars) before use so a wrong
       offset is ignored rather than handed to ProcessEvent. One log line
       records which route won.

1.9.1  REVERTED the 1.9.0 early-bus change. MY REGRESSION, OWNED.
       1.9.0 ended the warmup hold once the lobby "stopped filling". That
       measured the wrong thing: AGameModeBase::NumPlayers counts a player the
       moment their connection is accepted, but their client then spends a long
       time streaming the island. The warmup is most of that head start.
         45s hold  -> joined 01:28:02, bus 01:28:55 = 53s head start (played)
         15s hold  -> joined 02:12:41, bus 02:12:59 = 18s (quit on loading)
       Both reached EnterAircraft, so the SERVER LOG LOOKED IDENTICAL AND
       HEALTHY in both. Only a screenshot revealed the regression.
       LESSON WORTH KEEPING: a healthy server log is not evidence the player
       had a good experience.
       ServerReadyToStartMatch is not a usable substitute either — it fired
       ~20s before the bus and the client was still streaming after landing.

1.9.0  REGION-AWARE HOST DEMAND (kept — this one is good).
       getHostDemand asked hasLiveGameServer, which reused resolveGameServer's
       deliberately region-BLIND last fallback. Right for routing a player
       already in flight (a 300ms match beats a dead connect); wrong for "does
       this region need a host". Effect: ONE server anywhere in the world made
       needsHost false for EVERY region — no second host was ever elected and
       distant players were routed across the planet. The carefully written
       65%-proximity election never got a say because the demand it reacts to
       was already answered.
       Fix: resolveGameServer takes regionStrict; only hasLiveGameServer uses
       it. Routing untouched, still never returns null. Callers that send no
       region are unaffected.
       NEW TESTS: Main backend/src/services/matchmaking/regions-election.test.ts
       (13 tests). Verified they FAIL against the old code (2 fail / 11 pass)
       and pass with the fix. Full suite: 258 tests, 0 failures.

1.8.9  HOSTING RESTORED. ProcessEvent handoff. VERIFIED IN PLAY.
       Hosting aborted with "Unable to find ProcessEventAddress aborting..".
       Reboot's pattern scan for ProcessEvent is INTERMITTENT on 7.40 — the
       same DLL, same machine, same base address: missed 21:42, 21:52;
       resolved 0x38e340 three times 22:01-22:02; missed 22:14, 22:34. The
       function even MOVES between runs (0x38e340 one session, 0x1b4b0d0
       another), consistent with the packed exe decrypting differently.
       Two earlier conclusions in KNOWN_ISSUES were WRONG and are corrected
       there: Cobalt does NOT use Memcury for this (its kProcessEvent is
       character-for-character Reboot's own 4.22 pattern, and its FindPattern
       is a port of Reboot's), and the MinHook detour is not the cause (three
       processes installed the hook ~21s in and THEN resolved the pattern).
       Fix: Cobalt resolves this address in EVERY logged session and proves it
       by making thousands of calls through it, so it now exports
       NovaGetProcessEventAddress (captured at Init, before its own detour) and
       Reboot prefers it when its own scan returns nothing — RANGE-CHECKED
       against its own module first, because an address on the wrong function
       is worse than a clean abort.

1.8.x  The intro bumper (VERIFIED WORKING). Plays on entering Battle Royale,
       unskippable, with its own audio, the game's music silenced underneath
       and one track restarting from the top when it ends. On/off switch in
       Settings. See the "nova-bumper" memory and KNOWN_ISSUES for the long
       story (the short version: a MediaTexture you construct yourself has no
       rendering resource; load the GAME'S OWN asset instead — and NEVER
       vtable-guess, that froze the game in 1.8.0).

ALSO FIXED ALONG THE WAY (2026-09-19): the installed nova-proxy was CORRUPTED

7. TRAPS THAT HAVE ALREADY BITTEN — DO NOT REPEAT
-------------------------------------------------------------------------------

  * A UFunction path names the class that DECLARES it. "/Script/UMG.
    UserWidget.SetVisibility" is NULL because SetVisibility is on Widget. Use a
    class-chain walk. A silent `if (auto fn = Find(...))` around a lookup that
    can fail will hide this for releases at a time.
  * Likewise a rep notify is named after its property: OnRep_QuickBar implies
    the property is "QuickBar". That is how 1.9.2's bug was found.
  * NEVER bound a scan by an arbitrary count. A cap of 8 on the sound-class
    mute meant the base class was never reached and the whole feature silently
    did nothing while logging "ok".
  * NEVER guess a vtable slot and call it. 1.8.0 did and froze the game. A
    verification that accepts a value it should reject ("width > 0" accepting
    2 when the video is 854 wide) is worse than no verification.
  * The launcher ships a COMPILED backend snapshot that main.rs prefers over
    source. It went a month stale once and hid three shipped-as-fixed P1s.
    ALWAYS run tools/stage-backend.mjs before a release.
  * Server logs looking healthy proves nothing about what the player saw.
  * Both the client and the headless host write to cobalt.log. Do not infer
    ordering across processes from line order.
  * `npx tsc` installs the WRONG package. Use Main backend/node_modules/.bin/tsc.
  * Reboot/Cobalt source files are CRLF. Patch them with a script that
    preserves line endings, or the edit will not match.
  * Git Bash mangles `dumpbin /nologo` into a path. Use PowerShell for dumpbin.
  * Cobalt's import table must not grow. It is 9 DLLs. Check with dumpbin
    /dependents after every Cobalt change (winmm is lazy-loaded on purpose).
